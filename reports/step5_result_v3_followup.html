Part I — Conclusions

What each task actually showed, stated plainly.

Bottom line. Every open question these three tasks could test came back negative or non-committal — never “HGT wins.” Task 1 shows two of the three depth priors' own theoretical derivations don't describe either the measured graph or the model actually built. Task 2 shows HGT's consistent shortage loss to GraphSAGE can be made to disappear (a tie, not a reversal) by merging its thinnest relations' parameters. Task 3 — a genuinely different experiment giving the graph a real causal signal that provably didn't exist before — lands on the same tie by a completely different mechanism. No result in this round shows HGT winning under the 5-seed sign-consistency standard used throughout this project.

1

Were h² / h³ ever the empirically-correct targets?

Independent of the co-parent question. docs/project_HADES.md §4.2 derives each task's depth from a “path from a Supplier”: delay = h² (children + co-parents), shortage = h³ (Supplier→Component→Product + warehouse context), impact = h³ (→Product→rev_ORDERED→Order, an Order/Customer target).

At most one of three tasks (shortage) has a depth prior that's empirically correct on its own theoretical terms — and even that one didn't survive 5-seed testing in the main v3 round (Claim 2). This independently reinforces Claim 2 from a different angle: reach structure, not depth-sweep AUCs. The disconnect looks like it's between “information becomes available at hop k” and “reading from hop k specifically improves prediction,” not a matter of picking the wrong hop-count.

Co-parent reach, reconfirmed at 800-supplier scale: 0 / 800 — unchanged from the original v3 round. This is what Task 3 addresses directly, as a separate experiment.

2

Does merging HGT's thinnest relations close the shortage gap?

The four thinnest meta-relations (MANUFACTURED_AT 1,933 edges, SUPPLIES 2,400, STOCKED_AT 3,194, USED_IN 7,092 — a real gap before the next-thinnest at 15,608) were merged onto one shared SAGEConv parameter set, while the other 12 kept full per-relation HGT parameterization.

The consistent loss disappeared — it became a statistical tie, not a win. The delta itself isn't seed-consistent in either direction. Evidence in favor of the thin-relation-overfitting hypothesis as part of the explanation, not a demonstration that HGT is the better architecture once fixed.

3

Does a real co-parent signal let HGT win?

Separate · optional experiment

A new component_suppliers junction table gives ~17.5% of components (420 / 2,400) a second qualified supplier, with a real causal coupling — a co-parent's own latent stress bleeds into its partner's (coupling = 0.35), discoverable only by traversing the edge, not from either supplier's own history. This required a new dataset generation, DB reload, and a distinct run set — it does not exist in v1/v2/v3 at all.

Precondition re-verified first: co-parent 2-hop reach is now 449 / 800 (56%), versus 0/800 on base v3 — the structural condition docs/06 §6.1 always assumed is now genuinely true.

Neither task shows a consistent HGT advantage, even with a real, reachable co-parent signal newly present. Not reframed as “HGT wins” — the result is inconclusive/noise on both tasks, the same qualitative category as Task 2's finding, reached by a completely different mechanism. Two independent interventions — merging thin relations, adding a real relational signal HGT alone should be positioned to exploit — both land on a tie. This is the strongest evidence yet that HGT's shortage weakness is an architecture-vs-task mismatch these interventions don't resolve, not a data-availability problem.

Reminder of scope: this dataset is a separate, fourth generation, not “v3 plus one table.” Because the coupling feeds shipment-delay branching (a control-flow-dependent draw), the whole generated world differs from base v3 from that point forward. Still fully deterministic and passes every validation check. v3's own findings and governance rows are unaffected.

Task 2 — Sparse-relation-merged HGT encoder

Thinnest meta-relations (edge count at the largest snapshot): MANUFACTURED_AT 1,933, SUPPLIES 2,400, STOCKED_AT 3,194, USED_IN 7,092 — a real gap before the next-thinnest, SHIPS_FROM→Supplier at 15,608.

Encoder design. Merging required a custom encoder, not a metadata relabel — HGTConv's weights are keyed strictly by the full (src, rel, dst) triple, and the four thin relations don't share a common source or destination type. The mechanism: one SAGEConv(hidden, hidden) instance per layer, passed into HeteroConv under all 8 thin-relation keys — the same Python object, so its parameters and every gradient update are genuinely shared across all 8. The other 12 meta-relations keep full per-relation HGT parameterization. Verified via parameter count: 668,448 (sparse) vs. 701,088 (plain hgt) encoder parameters, plus a passing NaN/shape integration test.

Task 3 — Real causal co-parent signal

Schema. New component_suppliers junction table, mirroring product_components's validity-window pattern — secondary qualified suppliers beyond the mandatory components.supplier_id primary.

Generator. 420/2,400 components (17.5%, within the requested 15–20%) get a second qualified supplier via a dedicated, isolated RNG stream. stress() was split into own_stress() (a supplier's own factors, unchanged from before) and a new stress() that adds 0.35× each co-parent partner's own_stress — never the partner's coupled stress, avoiding mutual recursion. Suppliers with no partner (~82.5%) see identical behavior to base v3. Three new validation checks added (all pass): dual-source fraction in range, FK integrity, mutual partnerships.

Builder. The SUPPLIES/rev_SUPPLIES edge SQL now unions the mandatory primary with any component_suppliers rows valid as of t0 — a no-op on a graph with an empty junction table, edges added only here.
